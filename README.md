# Matrix Web Client E2E Test

Минимальный E2E-проект на Playwright JavaScript для проверки базового пользовательского сценария в веб-клиенте мессенджера на базе Matrix:

1. пользователь логинится;
2. открывает существующую комнату;
3. отправляет уникальное текстовое сообщение;
4. видит это сообщение в ленте комнаты.

## Почему выбран сценарий с существующей комнатой

Для E2E-проверки отправки сообщения выбран уже существующий room. Это уменьшает зависимость теста от бизнес-логики создания комнат, прав доступа, инвайтов и серверных настроек Matrix. Тест проверяет основной пользовательский путь, описанный в задании: открыть комнату, отправить сообщение, увидеть его в timeline.

## Требования к тестируемому клиенту

Все локаторы в тесте создаются через Playwright `.locator(...)`. CSS-селекторы строго следуют конвенции `data-qa-verified-*`. Это обязательный UI-контракт для приложения.

Ожидаемые атрибуты:

| Элемент | Атрибут |
| --- | --- |
| Форма логина | `data-qa-verified-login-form` |
| Поле логина | `data-qa-verified-login-username` |
| Поле пароля | `data-qa-verified-login-password` |
| Кнопка входа | `data-qa-verified-login-submit` |
| Оболочка залогиненного клиента | `data-qa-verified-authenticated-shell` |
| Список комнат | `data-qa-verified-room-list` |
| Элемент списка комнат | `data-qa-verified-room-list-item` |
| ID комнаты на элементе списка | `data-qa-verified-room-id="<room id>"` |
| Заголовок открытой комнаты | `data-qa-verified-room-header` |
| ID комнаты на заголовке | `data-qa-verified-room-id="<room id>"` |
| Лента комнаты | `data-qa-verified-room-timeline` |
| Сообщение в ленте | `data-qa-verified-timeline-message` |
| Текст сообщения | `data-qa-verified-message-text` |
| Состояние ошибки отправки | `data-qa-verified-message-send-error` |
| Поле ввода сообщения | `data-qa-verified-message-composer` |
| Кнопка отправки | `data-qa-verified-send-message-button` |

## Установка

```bash
npm install
npx playwright install chromium
```

## Настройка окружения

Создайте `.env` по примеру `.env.example` или передайте переменные окружения напрямую:

```bash
BASE_URL=https://your-matrix-web-client.example
E2E_USER_NAME=qa_user
E2E_USER_PASSWORD=change_me
E2E_ROOM_ID='!existing_room_id:matrix.example'
E2E_LOGIN_PATH=/
```

Описание переменных:

| Переменная | Назначение |
| --- | --- |
| `BASE_URL` | URL веб-клиента |
| `E2E_USER_NAME` | логин существующего пользователя |
| `E2E_USER_PASSWORD` | пароль существующего пользователя |
| `E2E_ROOM_ID` | стабильный Matrix room id существующей комнаты |
| `E2E_LOGIN_PATH` | путь к странице логина, по умолчанию `/` |

## Дополнительные проверки в тесте

Кроме основного сценария тест проверяет:

- пользователь действительно попал в залогиненную область клиента;
- открыта именно нужная комната по стабильному `room id`;
- поле ввода доступно для редактирования;
- кнопка отправки становится доступной перед отправкой;
- после отправки composer очищается;
- сообщение не только присутствует в DOM, но и видимо пользователю в viewport;
- у отправленного сообщения нет состояния ошибки отправки.

## Best practices, использованные в проекте

- секреты и URL не зашиты в код, а передаются через переменные окружения;
- сообщение генерируется уникальным для каждого запуска;
- тест разделен на читаемые `test.step`;
- page objects реализованы как классы страниц;
- классы страниц отделяют пользовательские действия и локаторы от сценария;
- все обращения к UI-элементам идут через `.locator(...)`;
- включены trace, screenshot и video на падениях;
- добавлена проверка `data-qa-verified-*`-конвенции селекторов;
- все пользовательские переменные названы в `snake_case`.

## Допущения

- У тестового пользователя уже есть доступ к комнате `E2E_ROOM_ID`.
- Клиент поддерживает логин по username/password. SSO-flow в рамках задания не реализован, потому что он зависит от конкретного identity provider.
- Приложение предоставляет QA-атрибуты из раздела "Требования к тестируемому клиенту".
- Тест не создает новую комнату намеренно: это отдельный рискованный setup-flow, который лучше покрывать отдельным E2E или API-fixture.

## Что не реализовано и почему

- Публикация в удаленный Git-репозиторий не выполнена: для этого нужны доступы к GitHub/GitLab и имя целевого репозитория.
- Проверка через реальный Matrix/Element instance локально не выполнена: в рабочей директории нет тестируемого приложения и учетных данных.
- CI pipeline не добавлен, чтобы не привязываться к конкретной платформе. Для GitHub Actions достаточно добавить job с `npm install`, `npx playwright install chromium` и `npm test`.
